# Made in code

Two projects, each built mostly by Claude Code in a day or two, with every picture and
sound generated by code:

- **A 23-minute animated explainer film** in a firelit linocut storybook style. It has 27
  scenes, a 24-character cast of SVG puppets, TTS narration timed to the word, and a
  music and SFX mix. Playbook: `references/film.md`.
- **Ashen Throne**, a Souls-like 3D boss fight in the browser: a procedural knight and
  boss, a castle, VFX and a synthesised orchestral score, all in about 19k lines of
  three.js with zero binary assets. Play it at https://ashen-throne-game.vercel.app.
  Playbook: `references/game.md`.

Read the playbook for the thing being made before writing any code. Each one has
calibration numbers, the pipeline, small drop-in snippets, the brief template used for
parallel builders and, most usefully, a list of traps written as symptom, cause and fix.

## The laws both projects share

1. **Direction before code.** Write one page setting out the look, a colour code where
   each colour means something, and two or three signature moves that recur. Pitch three
   directions, pick one and kill the other two. Without this page, parallel builders
   produce a patchwork.
2. **Contracts before builders.** Freeze the shared interfaces first: units and axes,
   timing tables, a file owner for every file, and "add but never rename". Then fan out
   parallel subagents, each owning disjoint files and working from a written brief.
   Contracts are what make parallelism safe.
3. **Draw with code, and keep it deterministic.** Seed every random number. Drive every
   animation from a seekable clock, never wall time. Identical output on every run is
   what lets you re-render, diff and debug.
4. **Claude checks its own work with instruments, not vibes.** Film: render stills at
   exact timestamps and look at them, measure loudness, verify word timings. Game: run
   headless Chromium on the real GPU, take scripted screenshots, let a bot fight the boss
   and log the win rate, and use a perf harness. "It compiled" proves nothing.
5. **Keep one build loop running.** Build the smallest end-to-end version first (one
   scene rendered with audio, or one arena with a fighting player), then layer on. Never
   swap a working product for unfinished complexity.
6. **Licences are part of the build.** Keep a `LICENCES.md` for every third-party asset
   (CC0 or CC-BY music and SFX), and get permission before monetising a derivative of
   someone else's work.

## How to run a session

1. Ask for the brief in one round: the subject or source, the audience, the length or
   scope, the look they are imagining, and any hard rules (for example no image models,
   or which APIs are allowed). Push back on a thin brief; it costs hours later.
2. Write DIRECTION (and SCRIPT for a film, or ARCHITECTURE with its contracts for a game)
   and get sign-off before building.
3. Build the thin end-to-end slice yourself, then fan out builders using the brief
   template from the playbook.
4. After every builder returns, verify with the instruments above before accepting its
   work. Re-read the traps list whenever something looks off; it has probably happened
   before.
5. Ship: master and render thumbnails for a film; deploy static to Vercel or similar,
   with OG tags, for a game.

## Budget honestly

These are big runs. The film took about 14 hours and roughly US$490 of model usage at
API prices across about 7 parallel builders. The game took about 5.5 hours wall clock,
with each builder using a few hundred thousand tokens. Tell the person the likely scale
before fanning out, and suggest a Claude subscription over pay-as-you-go API billing for
work this size.
